    Who handles what

    What native HTML, UI Kit and the application each handle in this case
    Handled byWhat
    Native HTML
    • <form novalidate>, the submit and reset buttons
    • Page title, language and section structure
    • The error summary's structure (a heading and a list of links)
    • role="status" for the success message
    UI Kit
    • Associating each field with its label
    • Required state (required is exposed as required)
    • Forwarding aria-describedby and aria-invalid from the component to its inner control, and updating the description when the error text changes
    • Not announcing untouched required fields as invalid (Safari+VoiceOver would otherwise)
    • The radio group's name and arrow-key behavior
    • Checkbox semantics
    • Taking part in the form through ElementInternals: validity, FormData, restoring values on reset
    The application (your code)
    • Validation rules and error messages
    • Writing the message next to the field and setting aria-invalid
    • Building the error summary and moving focus to it on submit
    • Summary links that put focus on their field
    • What happens on success (here, only a message)
    • Clearing errors, the summary and messages on reset
    • Wording and translation

    UI Kit does not decide what counts as an error and does not build the error summary for you. All of this case's application code is in form-registration.js; you can take it and adapt it.

    How it works

    1. Put an error element next to each field and reference it with aria-describedby. Keep it empty while there is no error. A referenced element is read by screen readers even when it is hidden, so clear its text instead of only hiding it with CSS.
    2. Check every field on submit. Read the component's validity (for example valueMissing or typeMismatch), write the message and set aria-invalid="true" on the component.
    3. When there are errors, show the error summary and move focus to it. People hear how many problems there are first, then each one.
    4. Summary links put focus directly on the field. They call the component's focus(), which lands on the real input inside the component.
    5. After the first submit, re-check a field when it changes. A fixed error disappears at once and the summary is updated without moving focus; when everything is fixed the summary closes.
    6. On success, announce the result with role="status" and leave focus where it is. The submit button stays on the page, so focus is not lost. Keep the status element on the page while it is empty.
    7. On reset, clear what the application added. The components restore their own values.

    Verification record

    Status: automated tests and Safari+VoiceOver checks done, with two known issues (below).

    Environment

    • UI Kit 3.0.2
    • macOS 27.0.1, Google Chrome 156, Safari 27.0.1 (October 2026)

    Automated test (test/browser/form-registration.mjs)

    Run in Chrome and Safari, each over http and from a local file, using only the keyboard. All passed:

    • Empty submit: focus moves to the error summary, which lists four fields; each field is marked invalid and has its message
    • Every summary link puts focus on the real input inside the component
    • After the name is corrected, its error disappears, the summary lists three problems and focus stays in the form; a malformed email gets the format message
    • Choosing a meal and agreeing to the terms with the keyboard; once everything is fixed the summary closes
    • Valid submit: the success message appears in role="status", focus stays on the submit button, and FormData has the values of all four components
    • Reset: the components return to their initial values and errors, summary and messages are cleared

    Checked in Chrome only:

    • The browser's accessibility tree: the four fields' names, required state (except the checkbox, which has no required state in ARIA), invalid state, and the error message as their description
    • No horizontal scrolling at 320px wide
    • axe-core 4.12.1 (WCAG 2.0–2.2 A/AA rules): no violations

    The automated test reads what the browser gives to assistive technology; it cannot tell how a screen reader actually speaks it.

    Safari+VoiceOver

    VoiceOver was driven with AppleScript, sending keys and reading back exactly what it spoke at each step. VoiceOver used a Traditional Chinese voice, so its own words (such as "required" or "invalid data") were spoken in Chinese. Safari kept its default settings, so links were reached with Option+Tab.

    • Field names, the required state, the radio position (for example "1 of 3") and the group name "Meal (required)" are spoken; arrow keys move between meals and Space toggles the checkbox
    • Before submitting, no field is announced as invalid
    • Empty submit: "There are 4 problems to fix" is spoken and the list has four links
    • From a summary link to its field: each field is spoken with its message and as invalid
    • Corrected fields lose both the message and the invalid state*
    • Valid submit: the success message is spoken, and spoken again on a second submit*

    * Checked on the Traditional Chinese version of this page, which used the same code before it was translated; typing could not be automated with the test Mac's input method afterwards.

    These checks found and fixed two problems. The success message was first hidden with display: none while empty, so Safari+VoiceOver never announced it (Chrome's automated check did not notice); the status region now stays on the page and the automated test guards it. And empty required fields were announced as "invalid data" as soon as the page loaded, as Safari does for plain <input required> too; since 3.0.2 the components mark their inner controls aria-invalid="false" until you set aria-invalid.

    Known issues

    • A description is read twice for the notes hint and the checkbox error. The component host keeps the aria-describedby you set, so the host is also exposed as a group with the same description. Fixing it changes the API and is planned for a later minor release.
    • Full-width characters: an email address typed with an East Asian input method in full-width mode (for example "ｍｉｎｇ＠ｅｘａｍｐｌｅ．ｃｏｍ") fails the format check, and the message does not suggest switching to half-width characters.

    Not tested

    • NVDA and JAWS on Windows, TalkBack on Android, VoiceOver on iOS
    • Firefox and Edge
    • Voice control, switch access and other assistive technologies
    • Testing with disabled people using the form

    This case describes how this form flow behaves in the environments above. It does not mean a whole site built with UI Kit meets WCAG.
