Accesserty UI Kit Dialog

Key Point

  • Use the native dialog element. As a modal it moves focus in, keeps Tab inside, makes the page behind it inert, closes on Esc and returns focus to the button that opened it.
  • Open and close it with Invoker Commands: command="show-modal", close and request-close, with commandfor naming the dialog.
  • Decide what closes it with closedby, and stop accidental closing of unsaved work by handling the cancel event that request-close and Esc fire.
  • Name every dialog with aria-labelledby pointing at its heading, and place initial focus with autofocus on the safest control.

There is no command for a non-modal dialog, so its button calls show(). A <dialog open> written in HTML is also non-modal. When users must finish the task first, use a modal. 

<button type="button" command="show-modal" commandfor="confirm">Delete file</button>
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Delete this file?</h2>
  <button type="button" command="close" commandfor="confirm" autofocus>Cancel</button>
</dialog>

closedby: who can close it

Click Outside to Close

closedby="any": clicking the backdrop, pressing Esc or the button closes me. Clicking my own padding does not.

Esc or the Button

closedby="closerequest": Esc or the button closes me; clicking the backdrop does not. This is the default for a modal.

Only the Button

closedby="none": neither Esc nor the backdrop closes me. Removing Esc takes away the exit keyboard users know best, so keep a visible close button.
closedby Backdrop click Esc Close button Use for
any Closes Closes Closes Information and settings
closerequest No Closes Closes Forms and important actions (modal default)
none No No Closes Rarely; always keep a visible close button

A browser without closedby ignores it and keeps the default: a modal closes on Esc but not on a backdrop click. closedby="none" blocks the user's close requests only; your own close() and requestClose() calls still close it.

Edit Note

You have unsaved changes. Discard them?

Type something, then press Cancel or Esc. Instead of closing, the dialog asks whether to discard your changes.

  • Cancel uses command="request-close". Like Esc, it fires a cancellable cancel event; calling preventDefault() keeps the dialog open.
  • The confirmation sits inside the dialog instead of window.confirm(), and receives focus so screen readers announce it.
  • Discard changes uses command="close", which does not fire cancel, so it closes without asking again.
  • Save submits the <form method="dialog">: the dialog closes and its returnValue is the button's value.
  • After closing nothing on screen says the note was saved, so the page announces "Note saved" or "Changes discarded" with ariaNotify(), or a live region where it is unsupported.
editor.addEventListener('cancel', (event) => {
  if (hasUnsavedChanges()) {
    event.preventDefault();
    showConfirmation();
  }
});
editor.addEventListener('close', () => {
  if (editor.returnValue === 'save') saveNote();
});

Accessibility Checklist

  • Give the dialog a name: aria-labelledby pointing at its heading.
  • Place initial focus on the safest control with autofocus, for example Cancel rather than Delete, or the first field.
  • Focus returns to the opening button automatically. If that button is removed while the dialog is open, move focus somewhere sensible yourself.
  • Always show a close button; not everyone knows Esc.
  • Do not interrupt with a modal for supplementary information; a popover or an expandable section is usually better.
